# V2: quality hold and customer-delivery recovery

The user-directed quality-hold revision replaces the original v2 shortage case.
V1 (`decision_demo.py`), its tests/configuration and the website are unchanged.
Three real Microsoft Agent Framework specialists and a Coordinator separate
**quality containment** from **delivery recovery**, using synthetic read-only
records. Both Decision-1 and GPT use existing **Azure Foundry deployments with
Entra authentication**. OpenAI-named packages are protocol adapters, not access
to the public OpenAI service.

## Frozen fictional case

Snapshot: **Thursday 15 October 2026, 14:00, UTC-05:00**. This is a scenario
clock, not a claim about current plant operations or today's date.

| Evidence | Fictional facts |
| --- | --- |
| Incident QI-2026-1042 | Tier-2 stamped mounting brackets, part MB-217, lot L-1042 |
| Lot reconciliation | 960 total = 720 onsite already Quality-held + 240 already shipped |
| Measured sample | 6 failures in 80 checked; total nonconforming units unknown, never extrapolated |
| Shipped exposure | SH-882 / ASN-019443; customer disposition unknown; responsible Quality notification pending |
| Usable stock | 180 from a different, independently released lot L-1038; held stock excluded |
| Customer schedule | SO-4821: Friday 180 at 10:00 and 240 at 16:00 = 420; first covered, second short 240 |
| Replacement offer | Separate lot L-1058, 300 units, collection possible; arrival and incoming acceptance unconfirmed |
| Authority | Dedicated quote DQ-3600 costs $3,600; planner limit $2,500; no approved concession |

Quality owns the hold, inspection and disposition. Agents never release held
stock, send notification, authorize spending or promise a delivery. A supplier
offer is not usable inventory. A changed customer window cannot close the
shipped-suspect containment issue.

## Setup and run (PowerShell)

Python 3.11+, Azure CLI, existing authorized Entra sign-in and existing Decision-1
and GPT Chat Completions deployments are required. No resources are provisioned.

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-v2.txt

$env:FOUNDRY_ENDPOINT = 'https://YOUR-RESOURCE.services.ai.azure.com'
$env:DECISION_DEPLOYMENT = 'YOUR-DECISION-1-DEPLOYMENT'
$env:LLM_DEPLOYMENT = 'YOUR-GPT-DEPLOYMENT'

.\.venv\Scripts\python.exe decision_demo_v2.py --help
.\.venv\Scripts\python.exe decision_demo_v2.py --example quality-hold
```

The last command makes **live, billable Azure model requests**. Help and offline
tests do not. Agent-issued smoke tests still need separately bounded approval;
local implementation approval does not authorize live inference.

`--example supply-chain` remains an alias for this revised case, preserving the
existing v2 startup command. `--endpoint`, `--decision-deployment` and
`--llm-deployment` override the same environment variables. The endpoint must
be an HTTPS Azure resource root, not a public OpenAI/project/inference URL, or a
URL containing credentials, port, query or fragment.
Decision-1 uses `https://cognitiveservices.azure.com/.default`; GPT uses
`https://ai.azure.com/.default` and `/openai/v1/chat/completions`.
Ambient public OpenAI keys and base URLs cannot replace this routing.

## Readable terminal flow

Normal output has **CASE / TEAM / FINDINGS / INITIAL PLAN / HUMAN CLARIFICATION /
UPDATED HANDOFF** sections. Each finding shows evidence, implication, sources and
next step. Selection/validation display chosen-option probability separately
from model-reported confidence. Technical UUIDs, payloads and per-call/tool
diagnostics stay out of the normal narrative. No blind truncation, extra
summarizer inference or cosmetic sleeps.

```powershell
.\.venv\Scripts\python.exe decision_demo_v2.py --example quality-hold --verbose
```

Verbose includes complete option distributions, typed findings/proposals,
fixture records, provenance, request/resume identifiers and dispatch/tool
counters. Quota waits, explicit errors and actual attempt totals remain visible
in normal mode too. Selection uncertainty can pause before expert dispatch;
the CLI does not fabricate skipped phases or force a model verdict.

## One natural clarification

Human review starts with a recommendation to **contact the customer planner
about rescheduling the second 240 units**, keeping the first 180 at Friday
10:00 unchanged. The actual model findings and proposal remain visible.
If the Coordinator did not recommend a customer-window review, this is explicitly
labeled a **host-suggested review step**, not a model recommendation.
Required owner handoffs stay in the plan/final output, followed by the concise
reminder: "Planning update only; quality release, containment and required
approvals remain separate."

Choose one of two options; no JSON or pipe-separated input is needed:

```text
1. Record customer response after contact: customer will move the second delivery.
2. Reject the recommendation and request leadership escalation.
Choose 1 or 2: 1
Quantity customer reportedly agreed to move (1-240): 240
Revised delivery time (YYYY-MM-DD HH:MM, UTC-05:00): 2026-10-17 08:00
Customer-planner response reference (1-200 characters): customer planner phone note
```

Choose 1 only to report a customer response received after contact, not merely
a willingness to reach out. This demo neither contacts the customer nor changes
an actual delivery date. Choice 2 (also `reject` or `escalate`) requests a
leadership handoff with no refresh or further model calls; it sends no message.
`reject`/`escalate` also stops during field collection.

The window uses the frozen snapshot's UTC-05:00 timezone. The reference is
required, nonempty and at most 200 characters; quantity must be a positive
integer no greater than the second delivery's 240 units; the revised time must
be later than its original window. Partial moves are supported. There is no
approve/release action.

The host creates a strict typed response through the real workflow
`request_info`/`response_handler` mechanism. Its source is **unverified human
clarification**. Reported agreement is not formal customer authority.
Production and Commercial refresh, Supply-chain reuses its finding, and
Coordinator/Decision-1 run once more. Unknowns can only disappear with relevant,
cited evidence; previous unresolved unknowns and conflicts cannot be dropped.

For the illustrative 240-unit move, the uncovered demand against the original
second window becomes provisionally 240 -> 0. **Inventory remains 180**, the
first delivery is unchanged, the later 240 still need replenishment, and
receipt/acceptance, formal customer review and shipped-lot containment remain
unresolved. Freight authority remains required if the proposal relies on freight,
even within a broader containment/recovery recommendation; a typed dependency
flag prevents the main action label from hiding that requirement.
Actual model recommendations/verdicts are not scripted.

EOF, interruption, non-TTY, invalid/empty input or expiry leaves review pending.
All prompts share the existing single 300-second human timeout and yield one
typed response through the same framework resume. No reprompt or automatic acceptance.

## Bounded calls and authority

Same three specialists, Coordinator, four tools and one continuation:
`read_inventory`, `read_shipment`, `read_build`, `read_approval_policy`.
Each specialist has at most 3 actual GPT attempts, 2 unique tools and 2 tool
rounds. Coordinator has one attempt and no tools. Existing reads can be batched
within a round; specialist dispatch remains sequential.

Hard ceilings remain **20 GPT + 3 Decision-1 = 23 actual attempts** and 12 tool
executions. Failed requests and tool-result turns count. With one batched tool
round per specialist, an all-three initial assessment uses 7 GPT + 2 Decision-1;
refreshing Production/Commercial adds 5 GPT + 1 Decision-1. These are illustrative
normal paths, not promises about live output or latency.

No SDK retries, repair calls or hidden loops. Transport/tool guards enforce
limits even when the framework requests another final completion. This process
paces at 10 GPT / 20 Decision-1 attempts per rolling minute; other callers can
cause 429, which stops without retry.
Request 60s, credential 15s, tool 2s, active 900s including quota waits, human 300s,
wall 1200s. Human waiting pauses only the active clock. Worst-case calls can
take minutes; time can expire before count ceilings.

The 0.70 probability policy is illustrative, not calibrated confidence, safety
or compliance assurance. Exit 0 is advisory completion or explicit reject/
escalate, never real-world authorization; exit 1 is execution/contract failure;
exit 2 is pending/unresolved handoff. This case normally retains Quality-owned
handoffs even with positive proposal validation.

## Offline development and research grounding

```powershell
.\.venv\Scripts\python.exe -m unittest -v
```

Tests run actual framework agents, tools, executors and HITL against fake Azure
credentials/transport. They cover lot/demand arithmetic, held-stock exclusion,
sample-versus-total distinction, typed customer windows, mapping/reuse,
containment persistence, rendering/verbose diagnostics, input termination,
Azure-only auth/URLs, failure handling, exact caps/deadlines and unchanged v1.
Mocked output is not live evidence. No live inference was performed for this
revision.

Workflow inspiration comes from primary IATF-hosted OEM requirements:
[Ford June2026 CSR](https://www.iatfglobaloversight.org/wp/wp-content/uploads/2026/06/Ford-IATF-CSR_Jun-2026-SCCAF_Final.pdf),
pages 32 (lot traceability), 34 (8.7.1.1, Ford-specific customer concessions) and
35 (8.7.1.6, shipped-nonconforming notification); and
[GM October2025 CSR](https://www.iatfglobaloversight.org/wp/wp-content/uploads/2025/10/IATF-16949-GM-Customer-Specific-Requirements-October-2025.pdf),
page 24 (10.2.3, containment/problem-solving).
These inform the distinction between containment, escalation and delivery
recovery, not universal OEM rules or a compliance determination. Ford's
specific concession systems and 24-hour notification rule are **not** imposed
as a generic workflow policy. Every case identifier, quantity, time and amount
above is fictional.

Core 1.21.0 / provider 1.15.0 and the installed SDK/transport remain pinned in
`requirements-v2.txt`; no feed overrides or TLS bypass.
